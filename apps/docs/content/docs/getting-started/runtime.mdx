## Architecture

Scripts run inside the bot Lua runtime and use supported APIs exposed as global tables. Core helper libraries in `Scripts/core` wrap those bindings into a stable, validated public API.

```
Your script (.lua)
    ↓
Core wrappers (Scripts/core/*.lua)
    ↓
Supported runtime APIs
    ↓
Tibia client
```

Lua runs cooperatively on the bot/game thread. Managed coroutines provide yielding and fairness; they are not background OS threads. Game reads/actions, script callbacks, and Lua state access remain serialized.

With the sandbox enabled, each user file has a private `_ENV`. Supported native/core globals are available through a restricted fallback. The top-level script body is a managed coroutine; after it finishes, the runtime starts `init()` from the same private `_ENV` if present. `init()` may call `wait`, HTTP, or WebSocket APIs.

A normal script stays alive while it owns runnable/sleeping coroutines, registered callbacks, scheduled events, HUD elements, or WebSockets. A script with no remaining work finishes automatically.

## Cooperative execution

Script execution is **cooperative**, not preemptive. The runtime can only switch to other work when your script yields control. Blocking the runtime with a tight loop will freeze the bot.

### Yielding correctly

Use one of these patterns for repeating or delayed logic:

| Pattern | Use case |
| --- | --- |
| `Module.Every(name, fn, delayMs)` | Repeating task on an interval |
| `Module.After(name, fn, delayMs)` | One-shot delayed callback |
| `Events.Schedule(fn, delayMs, ...)` | Owner-scoped one-shot schedule |
| `Module.New(name, fn, delayMs)` | Custom recurring module |
| `wait(ms)` | Yield inside a long-running coroutine |

HTTP and WebSocket operations also yield cooperatively while waiting. They must be started from a managed script coroutine (`init()` is managed and may call them).

**Avoid** busy loops:

```lua
-- BAD: freezes the runtime
while true do
    -- work without wait()
end
```

### Time

Use `Time.MonotonicMs()` for elapsed time, retry backoff, timeouts, and telemetry cadence. Compare two returned values; the epoch is unspecified. Do **not** use `os.clock()` for wall-time timeouts — Lua defines it as process CPU time.

### Lifecycle hooks

| Hook | Rules |
| --- | --- |
| Top-level body | Runs first as a managed coroutine |
| `init()` | Optional setup that may yield; prefer putting `Module.Every` here |
| `terminate()` | Protected synchronous cleanup only — cannot yield, 50 ms limit, runs at most once |

Do not start HTTP, WebSocket, scheduled, or module work from `terminate()`. Native owner-scoped resources are released automatically; use `terminate()` to restore intentional shared/live setting changes.

## Failure isolation and diagnostics

- `pcall` / `xpcall` retain normal Lua behavior. Expected errors you catch do not count as uncaught runtime failures.
- An uncaught top-level or `init()` error stops only that script.
- An uncaught repeating-module error stops that module. Sibling healthy modules keep running; if it was the only module, the script stops.
- An uncaught `Events.Schedule` error ends only that one-shot callback.
- A key, packet, or Walker event registration is disabled after **three consecutive** uncaught callback failures. One successful completion resets the counter.
- A Walker interceptor always releases its owned pause before failure policy runs.

Do **not** wrap an entire repeating module in `pcall` merely to print and continue. That hides genuine component failures from the runtime. Catch only errors the script can handle meaningfully, then recover or rethrow.

## Ownership, cleanup, and budgets

Key/packet/Walker events, scheduled events, HUD elements, HTTP results, WebSockets, sounds, and Walker holds are owned by the creating script. Teardown removes only that owner's resources.

Per script budgets include 64 MiB Lua memory, 256 managed coroutines, 64 pending event callbacks, and 32 outstanding async result tokens. Scheduler limits are 3 ms per coroutine resume, 4 ms per script per frame, and 8 ms for all Lua work per frame. Yieldable Lua is time-sliced. Deadline misses remain available as telemetry. The runtime circuit-breaks the offending component after **three consecutive** unpreempted resumes of at least **5 ms**, or one unpreempted **50 ms** resume. Delays are integer milliseconds from **0** through **86,400,000** unless a narrower function-specific range is documented.

Supported C++ exceptions from native bindings become contextual Lua errors and follow the same component policy. An ordinary C++ exception escaping a script tick quarantines that script. A native access violation is the exceptional emergency case: Lua execution is disabled for the client session, Walker ownership is released, and a dump is written. Diagnostics serialize error values without invoking user `__tostring` metamethods.

## Script lifecycle and cross-script control

- `Engine.Scripter.GetAvailableScripts()` lists exact runnable `.lua` filenames.
- `Engine.Scripter.Start(name)`, `Stop(name)`, and `Restart(name)` operate on those exact names.
- `Engine.Scripter.GetRunningScripts()` reports currently active script names.
- `Engine.Scripter.GetOutput(name)` returns current or most recently archived output (empty string when none).
- `Engine.Scripter.StopSelf()` is the only supported way for a running script to stop itself. Prefer it over the compatibility `Script.Unload()`.
- A script cannot `Stop` / `Restart` itself and cannot disable the sandbox or execute an arbitrary source string.

Every script writes its own runtime log under the product `UserData/BotLogs` area. Diagnostic/test scripts should print explicit `PASS` and `FAIL` lines.

## Sandbox file and module limits

- Sandboxed `io.open`, `os.remove`, and `os.rename` resolve inside the product user `Scripts` directory and cannot access `Scripts/core`. Individual file reads/writes are limited to **1 MiB**. Prefer `Storage` for normal script state.
- Sandboxed `require` loads text-only Lua modules from allowed script/library roots. Do not depend on native C-module loading or DLL search paths.
- Profile files use `Engine.Settings.Save` / `Load` (`.json`) and `Cavebot.Save` / `Load` (`.validuswpt`). Bare names search beside the script, then the product `Settings` / `Waypoints` folder. Loads are queued until Lua dispatch unwinds; loading Scripter settings can stop/restart the caller, and loading a waypoint bundle can stop waypoint scripts. See [Engine & Features](/docs/guides/engine-features) and [Cavebot](/docs/guides/cavebot).

## Nil-safe design

Many APIs return `nil` when:

- The player is not logged in or not available
- A required capability is not loaded
- Game state does not exist yet (e.g. no target, closed container, no NPC trade window)

Always validate before use:

```lua
if not Self.IsAvailable() then
    return
end

local hp = Self.GetHealthPercentage()
if type(hp) ~= "number" then
    return
end
```

Capability wrappers such as `Inventory` and `NpcTradeStorage` can return nil/false when the corresponding game state is unavailable. Check `IsAvailable` / capability methods where provided.

Getter tables from `Engine` are **detached snapshots**. Mutating them does nothing — call the matching setter.

## Module naming convention

Each module table is exposed in PascalCase. Some modules expose nested namespaces:

- `Cooldowns.Spell.IsReady(words)`
- `Cavebot.Walker.Resume()`
- `Engine.Healer.GetSpells()`
- `Engine.MagicShooter.GetEntries()`
- `Storage.Global.Get(key)`
- `Storage.Shared("name"):Get(key)`

Do not infer a `Query` or `Actions` namespace unless it is explicitly documented. Compatibility aliases are not part of the supported surface.

## Features API restriction

The Objects Dumper feature is reserved and intentionally blocked from public feature API paths. Do not attempt to enable, disable, or query it from scripts. Prefer `Engine.Features` for new scripts; the older global `Features` table remains for compatibility.

## Network constraints

- HTTP has no callback lifecycle API
- WebSockets use explicit `Receive`; there are no `onOpen`, `onClose`, `onError`, `onRedirect`, or automatic reconnect callbacks
- `validusbot.net`, its subdomains, and the registered service host are blocked
- A script may have at most four pending HTTP requests and four simultaneous WebSockets

## Hotkey constraints

- **alt** cannot be used with `Events.RegisterKeyEvent` / `Hotkeys.RegisterCombo`, but it is supported by `Hotkeys.SendCombo` / `Hotkeys.SendKey`
- Extended keys (insert, delete, home, end, page up/down, arrows) default to `extended = true` in `Hotkeys.ParseCombo`
- Standard Lua `table.concat` is allowed in sandboxed user scripts

See [Hotkeys API Reference](/docs/api-reference/hotkeys) for registration and send helpers.
